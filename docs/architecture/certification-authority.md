# Two certification authorities

**Status:** finding, with options. No semantics were changed by the change that
recorded this; current behaviour is pinned by
`packages/cli/src/certification-authority.test.ts`.

Anvil certifies bundles twice, with two models, and reconciles them in the CLI.

## What exists

| | `@anvil/generators/certify.ts` | `@anvil/certification` |
| --- | --- | --- |
| Size | 1,427 lines | 1,717 lines across 5 modules |
| Record | `Certification` | `CertificationRecord` |
| Status vocabulary | `passed \| failed \| expired` | `failed \| static_passed \| simulator_exercised \| certified \| expired` |
| Grouping | gates: `contract`, `semantic`, `safety`, `runtime` | phases: `static`, `executable`, `mutation` |
| Binds to | `bundleHash` over generated bytes | attestation: pack, contract, capability, surface-signature digests |
| Owns the artifact | yes — `certification.json` | no |
| Consulted by `anvil publish` | yes — `verifyCertification` | no |
| Described by an ADR | no | yes — ADR-0018 |

Both are real, both are tested, and neither is wrong on its own terms. The
problem is that there are two.

## The three specific consequences

**1. (Resolved.) ADR-0018 documented a status the product could not produce.**
The ADR says a pack is `certified` "only after its generated surfaces were
actually *started and exercised*, and if a deliberate safety regression cannot
slip through it." That status comes only from
`certify(air, { executable: true })`, which for a long time had no caller outside
`packages/certification/src/certification.test.ts`. It is now reached by
`anvil certify --executable` (`packages/cli/src/commands/certify.ts`), which
records `assurance.level: "executable"` and the engine's `engineStatus` in
`certification.json`. The default `anvil certify` remains static. The battery's
kill rule was tightened in the same change: a mutant counts as killed only when
a check fails against the weakened contract, never on the digest alone.

**2. The merge rule lives in a delivery adapter.** `runCertify`
(`packages/cli/src/commands/certify.ts`) runs both engines, maps the canonical
engine's checks into the generators engine's shape under a
`contract.certification-core.` prefix, decides `if (canonical.status === "failed")
cert.status = "failed"`, decides that a target-kit mismatch is a `contract`-gate
failure, and throws if the canonical status is outside the set its mode allows
(two statically, four with `--executable`). That is certification policy, and it
is in the CLI.

**3. Call sites disagree.** `approve.ts:388`, `capability-compose.ts:314`, and
`idempotency-store.ts:49` call `certifyBundle` directly — no bridge, no
target-kit check. So "is this bundle contract-clean?" has a different answer
depending on which command asks. Each call site is tested against its own
expectations; nothing tests that they agree.

## What this is *not*

It is not a fail-open. `anvil publish` requires fresh, hash-bound `selftest`,
`conformance`, and `simulation` reports, with prod failing closed and non-prod
waivers named explicitly in the plan. Executable evidence genuinely exists — it
simply runs through `anvil simulate` (which calls `runMutationBattery` and
`coverageMatrix` directly) rather than through the certification record's ladder.

The one soft edge: `assurance` is optional in the `Certification` schema ("older
records omit it and remain readable") and `verifyCertification` checks only
status and bundle hash. A record produced without the bridge therefore satisfies
the publish gate. That is a defensible compatibility choice, but it means the
canonical engine's verdict is advisory at the gate rather than required.

## How this happened

`@anvil/certification` was added by ADR-0018 as the certification authority. The
generators-side model predates it and owns the on-disk artifact that `publish`,
`status`, `approve`, and `sync` all read. Replacing the artifact would have been
a versioned schema migration across four commands, so the two were bridged
instead — and the bridge landed in the only place that had both, which was the
CLI. Nothing went wrong; the cheap step was taken twice and the expensive one
never was.

## Options

**A. Reconcile the ADR to shipped reality.** Done: the executable ladder is
wired to `anvil certify --executable` and ADR-0018's implementation status
describes what ships. Does not fix the split.

**B. Consolidate onto `@anvil/certification`.** Certification owns the record,
the status ladder, and the check registry over an abstract bundle view;
`@anvil/generators` supplies the view and renders the artifact. Requires a
versioned change to `certification.json` and touches `publish`, `status`,
`approve`, `sync`. Not behaviour-preserving. Dependency-wise it is clean — a new
`generators → certification` edge, no cycle, since `certification` does not
depend on `generators`.

**C. Keep both, with one owner for the boundary.** Declare the split deliberate —
byte-level bundle assurance versus contract-level attestation — move the merge
rule out of the CLI into a single module, and route every `certifyBundle` caller
through it. Fixes consequences 2 and 3, leaves 1 to option A.

## Recommendation

**A (done), then C, with B now a live option.** The merge rule leaving the CLI
(C) is the real architectural correction and is behaviour-preserving if the call
sites are aligned deliberately rather than incidentally — which is a semantic
decision, and so needs its own change and its own evidence.

B was only worth its cost if executable certification became reachable. It has:
`anvil certify --executable` mints `simulator_exercised` and `certified`, so
consolidating the record onto `@anvil/certification` is no longer consolidating
onto statuses nothing produces. Whether to take B is still a product decision
about what `certification.json` is, and it is not taken here.
