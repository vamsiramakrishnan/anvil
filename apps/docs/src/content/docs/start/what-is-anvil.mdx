Anvil is a compiler for agent-facing API tools.

An API specification describes transport. It usually does not prove business
effect, retry safety, confirmation policy, or approval. Anvil combines the
source contract with reviewed operational facts, compiles both into AIR, and
generates every agent surface from AIR.

```text
API contract + reviewed manifest -> AIR -> CLI / MCP / SDKs / skill / hooks
```

AIR is the Anvil Intermediate Representation. It is the only semantic model in
the generated bundle.

## Trace one operation

Consider `POST /refunds`.

The API contract can establish the path, request schema, response schema, and
auth scheme. It may not establish whether a retry can duplicate a refund.

The reviewed manifest supplies the missing facts:

```yaml
operations:
  createRefund:
    side_effect: mutation
    risk: financial
    reversible: false
    idempotency:
      strategy: required_request_key
      key_location: header
      header: Idempotency-Key
    confirmation:
      required: true
      reason: This operation moves money and cannot be reversed.
```

Anvil then applies five steps:

1. Capture the exact source bytes.
2. Combine source facts and reviewed manifest facts in AIR.
3. Validate effect, retry, confirmation, auth, and approval as one policy.
4. Generate every surface from that policy.
5. Recheck the policy in the runtime before network access.

Therefore, the refund keeps the same name, schema, confirmation rule, and
idempotency requirement in the CLI, MCP server, SDKs, skill, and hooks.

## One operation, several surfaces

<WhichSurfaceDiagram />

| Surface | Caller | Responsibility |
| --- | --- | --- |
| CLI | Developer or CI | Inspect and invoke approved operations with typed arguments |
| MCP server | Agent runtime | Expose approved operations as MCP tools |
| Client SDKs | Application code | Call the same approved operations from TypeScript, Python, Go, or Java |
| Skill | Agent | Discover capabilities, setup, constraints, errors, and examples |
| Harness hooks | Coding harness | Refuse or escalate earlier in the call path |

The surfaces are projections. They are not independent integrations.

Do not edit generated files. Change the API contract or reviewed manifest, then
recompile.

## Approval controls callability

Classification describes an operation. Approval determines whether callers
can use it.

<LifecycleDiagram />

| State | Meaning |
| --- | --- |
| `generated` | The operation exists in AIR |
| `review_required` | A missing fact or decision prevents safe exposure |
| `approved` | The operation may enter callable surfaces |
| `blocked` | A known condition prevents approval |
| `deprecated` | The contract remains recorded but is removed from normal use |

Only `approved` operations are callable. A name such as `getTransferStatus`
does not override missing evidence. An HTTP method does not establish business
effect. Approval follows inspection; it does not replace it.

## Safety rules

Anvil resolves policy with explicit conditions:

| If | Then |
| --- | --- |
| Effect is uncertain | Keep the operation `review_required` |
| Mutation idempotency is unproven | Disable automatic retry |
| Confirmation is required and absent | Return `confirmation_required` |
| Durable deduplication is required and unavailable | Fail the write closed |
| Host is outside the reviewed allowlist | Return `policy_denied` |
| A hook is unavailable | Enforce the same rule in the runtime |

Hooks improve feedback time. They are not the trust boundary. The runtime owns
the authoritative validation, auth resolution, idempotency, retry, host, and
execution checks.

## What a bundle contains

`anvil compile` writes three classes of artifact:

1. **Contract:** AIR, source identity, evidence, catalogs, and compiled policy.
2. **Projections:** CLI, MCP, SDKs, skill, hooks, mocks, evaluations, target
   kits, and deployment inputs.
3. **Assurance:** certification, self-test, conformance, simulation, and
   publication records bound to the bundle hash.

Run `anvil status <bundle>` when you resume work. It checks all three classes
and reports the first required action.

## Evidence follows the bundle

| Command | Question |
| --- | --- |
| `anvil certify` | Do generated artifacts agree with AIR? |
| `anvil selftest` | Does the generated MCP surface behave correctly over local transport? |
| `anvil conformance` | Do the generated CLI, MCP server, and skill agree? |
| `anvil simulate` | Do controls hold across the generated safety matrix? |

Each record identifies the bundle hash it tested. Change the bundle and the
record is stale. `anvil publish` requires current evidence, then prepares an
operator plan. It does not deploy.

## Separate input paths

Anvil compiles OpenAPI, Swagger, GraphQL SDL, proto3, WSDL, Google Discovery,
OData metadata, and Postman collections. Read
[source format support](/anvil/guides/source-formats/) for parser and wire
boundaries.

Gateway exports use the estate workflow because gateway identity, policies,
coordinates, and provenance must survive import.

Application-server, .NET, and broker configuration use the legacy workflow.
Legacy inventory records offline technical evidence and supports reviewed
capability bindings. It does not create or run a deployment-local bridge in the
current release.

Existing MCP servers use `anvil adopt`. Missing `readOnlyHint` metadata is
treated conservatively; the tool remains a mutation until reviewed.

## What Anvil does not own

Anvil does not:

- invent business meaning;
- approve an uncertain mutation;
- store production credentials;
- replace upstream authorization;
- fetch remote references during local source capture;
- turn a gateway or legacy inventory into execution authority; or
- deploy when `publish` runs.

These are enforced boundaries. Read the full
[product boundary](/anvil/concepts/product-boundary/) for ownership details.
