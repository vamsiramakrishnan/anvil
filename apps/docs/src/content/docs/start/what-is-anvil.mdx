Anvil is a compiler for agent-facing API tools. When no useful API contract
exists, it also provides an offline inventory and review protocol for legacy
invocation boundaries.

It reads an API contract, adds the operational facts the contract cannot
express, and generates a CLI, an MCP server, a skill, and enforcement hooks
from one model. The result is a reviewable bundle rather than a collection of
hand-written wrappers.

## The problem Anvil owns

An API specification describes transport well: paths, methods, fields, and
schemas. It often does not answer the questions an agent needs before acting:

- Does this operation only read data, or does it mutate state?
- Can a timed-out request be retried safely?
- Which value is the idempotency key?
- Is the effect reversible?
- Does a model confirmation suffice, or must a person approve it?
- Which operations belong together as one capability?

Hand-written integrations tend to answer those questions separately in a CLI,
an MCP tool description, and a prompt. Those answers drift.

Anvil records the answers once in AIR—the Anvil Intermediate Representation—and
generates every surface from that contract.

## One operation, several surfaces

<WhichSurfaceDiagram />

| Surface | Primary user | Role |
| --- | --- | --- |
| CLI | Developers and CI | Inspect and invoke approved operations with typed arguments |
| MCP server | Agent runtimes | Expose the same approved operations as MCP tools |
| Skill | The agent | Explain capabilities, constraints, setup, errors, and examples progressively |
| Harness hooks | Developers and operators | Refuse or escalate unsafe calls before they reach the runtime |

The surfaces are not independent implementations. An operation has one stable
identity, one input schema, one auth posture, and one safety contract. Each
surface projects that same operation for a different caller.

This leads to the most important maintenance rule:

> Do not edit generated files. Change the source contract or the Anvil manifest,
> then recompile.

## What is inside a bundle

`anvil compile` writes a self-contained directory. The files fall into three
categories:

1. **Contract** — `air.yaml`, source identity, evidence, catalog, and compiled
   manifests.
2. **Projections** — CLI, MCP, skill, hooks, mocks, evals, target kits, and
   deployment inputs.
3. **Assurance records** — certification, self-test, conformance, simulation,
   and release-plan evidence bound to the bundle hash.

`anvil status <bundle>` checks those categories and tells you the next safe
action. Use it as the entrypoint when resuming work on a bundle you did not
create or no longer remember.

## Approval controls exposure

Anvil distinguishes classification from authorization.

The compiler may infer that `GET /customers/{id}` is a read. That does not give
it authority to expose an uncertain transfer or deletion. Operations move
through a lifecycle:

<LifecycleDiagram />

- `generated` means the operation exists in the model.
- `review_required` means an unresolved fact or human decision prevents safe
  exposure.
- `approved` means the operation may appear in callable surfaces.
- `blocked` means a known condition prevents approval.
- `deprecated` retains the contract while removing it from normal use.

Only approved operations are callable. The generated skill may still name an
unapproved operation as unavailable so the agent understands the boundary and
does not invent a workaround.

Approval is not a substitute for evidence. Before approving, use `inspect`,
`assess`, and `lint` to understand the effect, risk, idempotency, auth, and
diagnostics.

## The manifest supplies missing meaning

An Anvil manifest is a reviewed YAML overlay. It records facts that belong to
the API owner but are absent from the transport contract:

```yaml
operations:
  createRefund:
    side_effect: mutation
    risk: financial
    reversible: false
    idempotency:
      strategy: required_request_key
      key_location: header
      header: Idempotency-Key
    confirmation:
      required: true
      reason: This operation moves money and cannot be reversed.
```

The manifest changes the canonical model, so every generated surface receives
the same update. Read [Write an Anvil manifest](/anvil/guides/manifest/) before
adding approval or retry semantics to your own API.

## Hooks improve the path; the runtime owns enforcement

Generated hooks can deny an unapproved tool or ask for confirmation before the
agent spends another turn. They are useful, but they are not the trust
boundary.

The generated runtime repeats the authoritative checks before contacting the
upstream API: input validation, confirmation, idempotency, host pinning, auth,
durable ledger requirements, retry eligibility, and response normalization.
If a hook is missing or a client does not support it, the runtime still fails
closed.

## Assurance is evidence, not a badge

The assurance commands answer different questions:

| Command | Question |
| --- | --- |
| `anvil certify` | Do the generated bytes and contracts still agree with AIR? |
| `anvil selftest` | Does the generated MCP surface work over the real local transport? |
| `anvil conformance` | Do CLI, MCP, skill, and runtime describe the same operations and posture? |
| `anvil simulate` | Do safety controls hold across the generated scenario matrix and injected regressions? |

Each result is tied to the current bundle hash. Recompiling or editing a bundle
makes prior evidence stale. `anvil publish` requires fresh evidence according
to the target environment, but it only prepares a deployment plan; it does not
deploy.

## Inputs and boundaries

Anvil accepts OpenAPI, Swagger, GraphQL SDL, gRPC/proto3, SOAP/WSDL, Google
Discovery, OData metadata, and Postman collections. Non-OpenAPI inputs are
lowered into the same protocol-neutral compiler pipeline before classification
and generation.

Support is intentionally specific. For example, saved Postman scripts are
reported but not executed, and the WSDL adapter supports a documented XSD
subset. Read [Source format support](/anvil/guides/source-formats/) before
planning around a non-OpenAPI input.

If the available source is application-server, .NET, or broker configuration
rather than an API description, use `anvil legacy inventory`. That workflow
captures technical observations, preserves conflicts, and lets a coding harness
propose one evidence-backed business operation for human review. It does not
lower the candidate into AIR or create an executable bridge in this release.
Read [Legacy application estates](/anvil/concepts/legacy-estates/) for the
separate lifecycle and current boundary.

Anvil also does not:

- infer business workflows without authored evidence;
- decide that an unknown mutation is safe;
- fetch remote references while locking a local source graph;
- hold your production secrets;
- deploy merely because `publish` was run; or
- replace the upstream API's own authorization and validation.

These are product boundaries, not missing prompts. See
[Product boundary](/anvil/concepts/product-boundary/) for the complete contract.
