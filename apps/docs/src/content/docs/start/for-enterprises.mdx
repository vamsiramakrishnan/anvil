Anvil scales only when ownership remains clear.

- The API owner owns business semantics.
- The platform team owns the compiler, runtime pattern, CI, and delivery path.
- Security owns the policy for sensitive exposure and execution.
- The agent team consumes approved capabilities; it does not approve them.

If the platform team invents business semantics, it guesses. If each service
team builds its own agent surfaces, those surfaces drift. Anvil keeps meaning
with the service owner and generation with the platform.

## Pilot admission criteria

Choose one service with:

- a real mutation with a visible consequence;
- an owner who can answer auth and idempotency questions;
- a usable API contract, or a gateway export paired with its authoritative API
  contract; and
- a mock or non-production endpoint for executable checks.

A read-only demo proves parsing. A payment, provisioning, or case-management
operation proves the review and runtime model.

For a legacy queue, EJB, or WCF endpoint, include the middleware owner. Treat a
reviewed binding as a design artifact until a deployment-local adapter exists
and passes assurance.

## Pilot exit criteria

The pilot is complete only when the team can reproduce:

1. the exact source bytes Anvil compiled;
2. the evidence behind every exposed operation;
3. the calls the runtime will refuse;
4. the assurance required for release;
5. the operator action that performs deployment; and
6. the response to source or policy drift.

Tool count is not an exit criterion.

## Adoption path

<JourneyDiagram />

### 1. Capture the source

Use content-addressed source snapshots. For gateway exports, run estate
inventory, audit, and planning before importing individual APIs. Do not flatten
an estate into one tool catalog.

### 2. Build a candidate

Use `anvil agentify` for an unfamiliar API. It captures, compiles, assesses,
and proposes capability groups. It then stops for review.

For legacy configuration, use inventory and candidate refinement. The output is
a reviewed, non-executable binding. It is not an onboarded runtime.

### 3. Add owner-reviewed facts

Keep `anvil.yaml` beside the source contract. Record stable names,
idempotency, confirmation, auth posture, retry constraints, and authored
workflows. Review the manifest like code.

### 4. Approve the smallest useful capability

Approval changes what the generated CLI, MCP server, and SDKs can expose.
Start with the minimum operation set that satisfies the use case. Do not approve
an entire service because one operation was reviewed.

### 5. Verify one bundle hash

Run certification, self-test, conformance, and simulation against the same
bundle. Generate target and ledger inputs before the final assurance pass when
those artifacts enter the certified hash.

`anvil publish` prepares an operator plan. The existing delivery system still
owns credentials, provider mutations, rollout, and rollback.

### 6. Reconcile drift

Recompile or run `anvil sync` when the source changes. A description edit, a
dropped confirmation rule, and a widened auth scope require different review.
Review semantic drift, not only file diffs.

## Ownership

| Decision | API owner | Platform | Security / risk | Agent team |
| --- | --- | --- | --- | --- |
| Maintain source contract | Owns | Supports | Reviews material changes | Consumes |
| Supply missing semantics | Owns | Provides schema and tools | Reviews safety-sensitive claims | Provides use cases |
| Approve exposure | Consulted | Runs the workflow | Owns sensitive-operation policy | Never self-approves |
| Build and verify bundle | Supports | Owns | Defines required gates | Consumes records |
| Deploy runtime | Provides upstream coordinates | Owns | Reviews IAM and egress | Registers endpoint |
| Resolve drift | Owns source change | Runs detection | Reviews safety loosening | Revalidates workflows |
| Confirm legacy binding | Consulted | Coordinates middleware owner | Reviews exposure | Does not infer semantics |
| Operate legacy adapter | Supports behavior | Owns adapter lifecycle | Reviews identity and network | Consumes approved surface |

## Map existing controls

| Existing control | Anvil artifact or gate |
| --- | --- |
| Source provenance | Content-addressed source snapshot |
| Change review | Manifest and capability decision in the service repository |
| Least privilege | Only approved operations enter callable surfaces |
| Separation of duties | Explicit operation review and human-approval policy |
| Release evidence | Hash-bound certification, self-test, conformance, and simulation records |
| Change detection | Semantic drift report with blocking policy changes separated from documentation changes |
| Secret management | Credential contract containing names and references, never values |
| Runtime egress | Reviewed host policy plus platform network controls |

Anvil should enter the controls already used for source review, identity,
secrets, deployment, and incident response. It is not a second organizational
control plane.

## Rollout sequence

### Pilot

- One service.
- One owning team.
- One consequential mutation.
- One approved capability.
- One mock or non-production runtime.
- One recorded list of unresolved gaps.

### Template

- Put source capture, compile, lint, and assessment in CI.
- Keep approval as a reviewed change.
- Require the same assurance gates for every bundle hash.
- Standardize runtime identity, secret references, egress, and telemetry.
- Publish one service-repository example.

### Scale

- Onboard through a written ownership contract.
- Publish approved bundles and skills through the existing catalog.
- Keep estate inventory separate from operation approval.
- Track failures by source, review, assurance, deployment, and runtime stage.

## Metrics that indicate progress

Track:

- time to first approved capability;
- percentage of candidate operations left `review_required`;
- review latency by missing claim type;
- assurance failure rate by lane;
- time to resolve blocking drift;
- percentage of live runtimes with current bundle evidence; and
- incidents caused by false source or manifest claims.

Do not optimize for generated tool count. A useful capability has a named
owner, a reviewed contract, current evidence, and an operated runtime.
