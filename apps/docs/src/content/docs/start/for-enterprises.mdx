Anvil scales through repeatable contracts, not through a central team rewriting
every API.

API owners keep responsibility for business semantics. A platform team provides
the compiler, CI templates, runtime boundary, and release policy. Security
reviews the small set of facts that change exposure or execution risk.

## Start with one consequential API

Choose an API that is representative, not convenient:

- it has at least one mutation with a real consequence;
- the owning team can answer idempotency and auth questions;
- a usable source contract exists, even if it is WSDL or a gateway export; and
- the API can be exercised through a mock or non-production endpoint.

A read-only demo proves parsing. A payment, provisioning, or case-management
API proves whether the ownership and review model works. If the pilot begins
from a legacy queue, EJB, or WCF endpoint, include the deployment and middleware
owners and treat the approved binding as a design artifact until a tested local
bridge exists.

The pilot is successful when the team can explain and reproduce:

1. which source bytes were compiled;
2. why each exposed operation is approved;
3. what the runtime will refuse;
4. which evidence is required before release; and
5. what happens when the source contract changes.

## The adoption path

<JourneyDiagram />

### 1. Capture the source

Import local contracts into immutable source snapshots. If the source of truth
is a gateway, use `anvil estate inventory`, `audit`, and `plan` before adopting
individual APIs. Do not flatten a whole estate into one unauditable tool list.

### 2. Compile and assess

Use `agentify` for discovery. It compiles the source, reports readiness, and
proposes capability boundaries without certifying or publishing the result.
Store the generated bundle as a candidate artifact, not as hand-maintained
source code.

When no useful API contract exists, replace this step with legacy inventory and
candidate refinement. The result is not a normal compiled bundle: it is a
reviewed, non-executable capability binding. Do not count it as onboarded until
the required deployment-local adapter, assurance, and operational ownership are
in place.

### 3. Enrich with the owner

The API owner supplies missing facts in `anvil.yaml`: stable names,
idempotency, confirmation, principal shape, retry constraints, and authored
workflows. The manifest is reviewed like code and stays next to the source
contract.

### 4. Approve narrowly

Approve operations and capability groupings only after inspection. An initial
release should expose the smallest useful capability, not every endpoint in the
service. A small approved surface is easier to evaluate, permission, and
operate.

### 5. Assure and release

Run static certification plus executable self-test, conformance, and simulation
against the same bundle hash. Generate target and deployment inputs, then let
the organization's existing delivery system apply them. `anvil publish`
prepares a plan; it does not bypass deployment controls.

### 6. Reconcile drift

Recompile or run `anvil sync` when the upstream contract changes. Treat a
dropped confirmation, widened auth, or new retry permission differently from a
description edit. Review the semantic contract, not only the generated diff.

## Ownership model

| Responsibility | API owner | Platform team | Security / risk | Agent team |
| --- | ---: | ---: | ---: | ---: |
| Maintain API contract | Owns | Supports | Reviews material changes | Consumes |
| Author missing semantics | Owns | Provides schema and tooling | Reviews safety-sensitive claims | Provides use cases |
| Approve operation exposure | Consulted | Executes workflow | Owns policy for sensitive operations | Does not self-approve |
| Build and assure bundles | Supports | Owns | Sets required evidence | Consumes results |
| Deploy MCP runtime | Provides upstream coordinates | Owns | Reviews IAM and egress | Registers endpoint |
| Respond to contract drift | Owns source change | Runs detection | Reviews safety loosening | Revalidates dependent workflows |
| Confirm legacy deployment bindings | Consulted | Coordinates middleware owner | Reviews resulting exposure | Does not infer from names |
| Operate a legacy bridge | Supports business behavior | Owns deployment and adapter lifecycle | Reviews identity and network boundary | Consumes the domain MCP surface |

Avoid a model where the platform team guesses business semantics for hundreds
of services. The compiler can detect uncertainty; only the service owner can
resolve many of those questions.

## Map Anvil to existing controls

| Existing control | Anvil control point |
| --- | --- |
| Source provenance | Content-addressed source snapshot and source hash |
| Change review | Manifest and capability review in the service repository |
| Least privilege | Only approved operations enter callable surfaces |
| Separation of duties | Human-approval policy and harness escalation |
| Release evidence | Certification, self-test, conformance, and simulation records bound to one bundle hash |
| Change detection | Semantic drift report with blocking safety changes distinguished from documentation changes |
| Secret management | Generated credential contract names required values; the runtime resolves values from the operator's secret system |
| Runtime egress | Allowed-host policy and deployment network controls |

Anvil should fit inside the delivery controls already trusted by the
organization. It is not a new control plane for approvals, secrets, or cloud
deployment.

## A practical rollout

### Pilot

- One service, one owning team, one meaningful mutation.
- Compile from the real source contract.
- Author and review the manifest.
- Approve one capability.
- Run the generated MCP server against a mock or non-production endpoint.
- Record the gaps that required manual interpretation.

### Template

- Put source capture, compile, lint, and assessment in CI.
- Keep approval as an explicit reviewed change.
- Require the same assurance lanes for every bundle hash.
- Standardize runtime identity, secret naming, egress, and telemetry.
- Publish a reusable service-repository example.

### Scale

- Onboard services through a documented ownership contract.
- Publish approved bundles and skills through the organization's existing
  catalog.
- Track time-to-first-approved-capability, review latency, drift response time,
  and failed assurance lanes.
- Keep gateway-estate inventory separate from capability adoption so ownership
  and authority remain explicit.

The useful scaling metric is not the number of generated MCP tools. It is the
number of capabilities with a named owner, a reviewed safety contract, fresh
assurance evidence, and an operational runtime.
